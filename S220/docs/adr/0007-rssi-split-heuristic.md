# ADR-0007: RSSI バイトの分離に改行位置と値域によるヒューリスティックを使う

- ステータス: 承認
- 日付: 2026-10-15

## コンテキスト

- PC 版 `split_rssi()` はパケットの**末尾 1 byte を無条件に RSSI** としている。
- この方式では、RSSI バイトが付いていないパケット（モジュール設定が無効、またはパケット境界判定のずれ）で、末尾の改行 `\n`（0x0A）が RSSI と誤認され **−246 dBm** という異常値が記録され、さらに改行が失われて次の行と連結されてしまう。
- 送信データは原則として `tx_app.py` 形式の改行終端テキストだが、サンプルコードのバイナリ（連番バイト列など）も受信できるようにしたい。

## 決定

`splitRssi(packet)` を以下の順で判定する。

1. 末尾が `\n` / `\r` → **RSSI なし**（パケット全体がペイロード）
2. 末尾から 2 番目が `\n` / `\r` → 末尾 1 byte を RSSI
3. 末尾から 3 番目が `\n` / `\r` → 末尾 1 byte を RSSI
4. 末尾バイト − 256 が **−150〜0 dBm**（値 106〜255）→ 末尾 1 byte を RSSI
5. それ以外 → RSSI なし

## 理由

- 改行終端テキストの場合、「テキスト + `\n` + RSSI」となるので、改行の位置から RSSI の有無を確実に判定できる。RSSI バイトがなければ 1. で弾かれ、−246 dBm の誤記録と改行の消失を防げる。
- LoRa の実用的な受信感度は −150 dBm 程度より上なので、値域 4. で明らかに RSSI でない値を除外できる。
- 判定はパケット単位の関数で完結し、単体テストで網羅しやすい（`RxCoreTest.testSplitRssi`）。

## 結果

- 改行終端テキストでは、RSSI バイトの有無にかかわらず本文を正しく取り出せる。
- **改行で終わらないデータで RSSI バイトが無効な場合**、末尾の 1 byte が 0x6A〜0xFF（ASCII の `j`〜`~`、UTF-8 マルチバイト文字の後続バイトなど）だと RSSI と誤認され、本文の末尾が欠ける。RSSI バイト有効を前提とすることで（[ADR-0006](0006-rssi-mode-and-packet-gap.md)）実運用上は問題にならないと判断した。
- RSSI バイトの値がたまたま 0x0A / 0x0D（−246 / −243 dBm）になることは物理的にあり得ないため、1. の判定で取りこぼすことはない。
- 2. / 3. は「改行の後に 1〜2 byte」の構成で常に末尾 1 byte を RSSI とするため、改行の後に短いデータが続くパケットでは誤判定し得る。
- PC 版 `split_rssi()` とロジックが異なる状態になっている。

## 検討した代替案

- **末尾 1 byte を無条件に RSSI（PC 版と同じ）**: 単純だが、上記の −246 dBm 問題が起きる。
- **値域判定のみ**: 改行 0x0A（−246）は除外できるが、改行終端テキストで RSSI バイトがない場合に最後の文字が削られるケースが残る。
